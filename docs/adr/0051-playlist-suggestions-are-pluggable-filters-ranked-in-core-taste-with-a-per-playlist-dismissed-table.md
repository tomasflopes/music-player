# 0051: Playlist suggestions are pluggable filters ranked in `:core:taste`, with a per-playlist `playlist_dismissed` table (schema v5)

Date: 2026-11-14 · Status: accepted

**Context.** Design 7.13 wants about ten suggestions under a playlist, built from artist, album and taste until sound analysis exists (phases 3 and 4), with "+" and "✕" and a negative signal for what is dismissed. Guidelines 2.4 asks for a new rule to be a new implementation behind a small interface. Scores are read through the `ScoreBoard` port (ADR 0023, 0049); adding a song goes through `AddSongsToPlaylist`, which writes the +3 `playlist_add_event` (ADR 0049).

**Decision.**
- *Filters:* `SuggestionFilter` (`id`, `isRelevanceCheck`, `points(candidate, context)`) in `:core:taste`, pure Kotlin. Four implementations, each registered with `@Provides @IntoSet` in `SuggestionModule`: `ArtistLinkFilter` (same main artist, or a featured link either way, through `SongArtistSource`), `AlbumLinkFilter`, `TasteScoreFilter` (song score and main-artist score, `tanh`-squashed) and `DismissedNeighbourFilter` (negative). A contract test runs against every filter.
- *Relevance versus ranking:* a song is suggested only if a relevance check (artist or album) gave points and the sum of all filters is above 0. Taste and dismissals only rank, so a loved song with no link to the playlist is never shown ("no pure random picks"). The sound-based checks of phase 4 are one more `@IntoSet` filter.
- *Use case:* `PlaylistSuggestions.observe(playlist, place)` combines the playlist songs, its dismissals and the library, drops members and dismissed songs, and ranks the rest with `SuggestionRanker` (best first, ties by song id, top `size` = 10). It re-emits on any change, so "+" and "✕" refresh the list at once. Taste scores are read once per collection, not followed, so the list does not move while the owner listens; artists are looked up once per song per collection.
- *Where:* the playlist page needs 1 song; the New playlist flow (the picker, which is where a new playlist is filled, ADR 0041) needs 2 (`SuggestionConfig.minSongsInPicker`, the design's "2-3").
- *"+" and "✕":* "+" calls `AddSongsToPlaylist`, the same path as every other add. "✕" calls the new `PlaylistDismissals` port.
- *Storage:* `playlist_dismissed (playlist_id, song_id, at)`, primary key `(playlist_id, song_id)`, schema v5, hand-written `MIGRATION_4_5` with an emulator test. **It cascades on playlist delete** (foreign key to `playlist`, like `playlist_song`): a dismissal means nothing without its playlist and ids are never reused (AUTOINCREMENT). This differs on purpose from the append-only logs (`play_event`, `playlist_add_event`), which keep their rows because they feed taste. `song_id` has no foreign key (ADR 0021, 0037).
- *Negative signal, per playlist only:* a dismissed song never reaches the global score or any log. It lowers the rank, in that playlist, of songs by the same main artist (`DismissedRule.artist` = 1.5 each) and on the same album (`album` = 1.0 each), counting at most `maxCount` = 3 dismissed songs of each. All numbers are in `SuggestionConfig` (defaults in code, like `TasteConfig`, ADR 0024).
- *Rule calls (owner can overrule):* points are artist link 3 (main) or 2 (featured), album 2, each boosted by `1 + ln(n)` for n playlist songs behind the link; taste is at most 1.5 (song) plus 1 (artist) either way; tapping a suggestion row does nothing (playing from suggestions is not asked for); the block sits at the end of the playlist page, and above the results of the picker while its search box is empty; a retired song is neither suggested nor counted, and its dismissal stays.

**Consequences.** Each refresh looks at every library song: `SongArtistSource.artistsOf` runs once per song per collection and the ranking is linear in the library; both run off the main thread and neither is measured on the phone (see the phase 2 file). `MIGRATION_4_5` runs only in the emulator test (`deviceCheck`, ADR 0009). The exported schema `data/schemas/.../5.json` is generated by the build and must be committed.
