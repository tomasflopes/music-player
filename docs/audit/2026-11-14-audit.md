## 4. The ten rules, by reading

| # | Rule | Result (all SUSPECTED) |
|---|---|---|
| 1 | Picked +3, except skipped in first 15 s | Matches. `startBonus` gives +3 unless the outcome is `SKIPPED_EARLY`. A picked row that ends `stopped` gets +3 even at 0 ms listened. |
| 2 | Completed +1 only under shuffle, mix, radio; >80 % = completed; stopped <80 % = 0 | Matches except the exact 80 % point (S5). |
| 3 | Skip bands | 14.999 s = -2, 15.000 s = -1, just under 50 % = -1, exactly 50 % = 0, 50-80 % = 0. Exactly 80 % counts as completed (S5). On a song shorter than 30 s, a skip under 15 s is -2 even when it is past 50 %. |
| 4 | Browsing burst | Matches: 3+ consecutive `SKIPPED_EARLY` rows, each start at most 60 000 ms after the previous one (60 001 splits); any other row ends the run; the settled song is untouched. Start and end of log are handled by the final `close()`. |
| 5 | Completed clears negatives before +1 | Matches for rows whose weight is negative. Misses the -1 inside a picked mid-skip row (S6). Rows with equal timestamps follow log order (S8). Other songs are untouched (per-song tally). |
| 6 | Decay | `0.5^(age / 30 d)` per event; 30 d = 0.5, 240 d = 0.00390625. The 240-day cut-off lives only in the DAO query, with the cut-off computed once per subscription (S7). A row exactly 240 days old is included. |
| 7 | Top 100 | Score > 0, in library (`in_library = 1`), best first, ties by latest row then id, cap 100, retired songs replaced by the next ones. Empty log gives an empty list. Deterministic for a given log. Not refreshed on library change (S3). |
| 8 | Unreliable rows | No crash and no NaN with the default config. Duration <= 0: completed only if `ended_by = completed`; stopped = 0; skipped under 15 s = -2 (-0.2 in a burst); skipped at 15 s or more = 0. Listened > duration: counts as completed, whatever ended it. Negative listened: skipped = -2, stopped = 0. Columns are NOT NULL, so "missing" can only be 0. See S10. |
| 9 | Sources | Every `PlaySource` falls into one rule: completion counts when `shuffle` is true or the source is `mix` or `radio`. Queue jump logs `picked` (`PlaybackEngine.jumpToUpcoming`); manual entries log source `queue`. A new source value silently gets "counts only under shuffle". |
| 10 | Invariants | Finite: holds. Same-timestamp permutation: does not hold (S8). Event beyond the horizon: no effect through the DAO, subject to S7. Later completed play never lowers the score: holds (its weight is >= 0 and it only removes negatives). |

## 5. Findings and possible fixes (all SUSPECTED)

| # | Sev | Finding | Possible fix |
|---|---|---|---|
| S1 | Medium | `PlayEventTracker` measures listened time with `System.currentTimeMillis`. A wall-clock change during a song distorts `listened_ms`: a forward jump can turn a skip into ">80 % = completed"; a backward jump is clamped to 0 and can turn a long listen into an early skip (-2). | Inject two clocks: wall clock for `started_at`, a monotonic one (`SystemClock.elapsedRealtime`) for durations. ADR-worthy. |
| S2 | Medium | A controller that seeks to a window index changes the song without the queue or the log knowing: `QueueAwarePlayer` does not override `seekTo(index, position)` / `seekToDefaultPosition(index)`, and `onMediaItemTransition` handles only `AUTO` and `REPEAT`. The new song's listening is booked to the old song's row. Known gap in ADR 0025. | Override both in `QueueAwarePlayer` and route them through a queue jump, or remove `COMMAND_SEEK_TO_MEDIA_ITEM` from the available commands. |
| S3 | Medium | `TopHundredProvider.songs()` maps only board emissions; `songsByIds` is a one-shot query. A song retired by a rescan stays in the list and card count (and a returning song stays out) until the next log insert. | Combine the board flow with a cheap library-change signal from `SongReader`, then re-run `inLibrary`. |
| S4 | Medium | The crash checkpoint is saved only on start and on play/pause changes, with listened-so-far at that moment. Killed after 3 uninterrupted minutes, the recovered row has `listened_ms` near 0. Top 100 effect is small (the row is `stopped`), but a >80 % listen loses its completed status and later stats under-count. | Store `playingSinceMs` in the checkpoint and compute listened on recovery, capped at the duration; or checkpoint every N seconds while playing. |
| S5 | Low | `SignalRules.outcomeOf` uses `fraction >= completedFraction`; the design says more than 80 %. Only the exact 80 % point differs. | Change `>=` to `>`. |
| S6 | Low | `TasteScorer` adds a row's start bonus and end weight before choosing the positive or negative tally. A picked song skipped between 15 s and 50 % is stored as +2, so a later completed play does not clear its -1. | Tally the bonus and the end weight separately (expose both from `SignalRules`). |
| S7 | Low | `OnDemandScoreBoard` computes `clock.millis() - horizonMs` once per collection, and `TasteScorer` does not apply the horizon itself. A long-lived collector keeps rows older than 240 days (at most 0.4 % weight, enough to keep a song above 0). | In the `map`, drop rows older than `clock.millis() - horizonMs` before scoring. |
| S8 | Low | Forgiveness and bursts depend on row order. With equal `started_at`, the DAO's `ORDER BY started_at, id` decides, so the result is deterministic but not permutation-invariant. If the clock moves back, a later row sorts earlier. Equal timestamps need two starts in the same millisecond. | Accept and document, or order by `id` (log order) instead of `started_at`. ADR-worthy if changed. |
| S9 | Low | `previous()` that only restarts the song logs nothing (ADR 0025), so the row keeps accumulating and can exceed the duration, which counts as completed. | End the row as `skipped` and start a new `nav` row on restart, or cap `listened_ms` at the duration. |
| S10 | Low | Phase 1 rows with `listened_ms = 0` and `song_duration_ms = 0` that ended `skipped` score -2 each (ADR 0025 accepts this). | Treat a skipped row with unknown duration as neutral. ADR-worthy. |
| S11 | Low | `TasteConfig` is not validated: `halfLifeDays = 0` gives 0/0 = NaN scores; a negative value inverts decay. | `require(halfLifeDays > 0)` and similar checks in `init` blocks. |
| S12 | Info | Scores are sums of doubles, so signals that cancel exactly on paper can land at about 1e-16 and pass `score > 0` (for example +2 and ten burst skips of -0.2). | Set `minScore` to a small epsilon such as 1e-9. |
| S13 | Info | Shuffling the Top 100 gives +1 per completed song and tapping one gives +3, so the list reinforces itself, which works against "a Top 100 that freezes". | Product decision: do not count completions or picks with source `top100`, or count them at a reduced weight. ADR-worthy. |
| S14 | Info | Picking another song while one is playing closes the playing one as `skipped`, so it can take -2. | Decide whether a pick should end the previous row as `stopped`. |
| S15 | Info | `TasteScorer.score` trusts the caller to pass rows oldest first; it neither sorts nor checks. | Sort defensively or `require` the order. |
| S16 | Info | Recompute cost is unmeasured. By reading: one pass over the rows plus a sort of the songs, but each log insert also re-reads every row of the 240-day window from Room and runs at least one `songsByIds` query. | Run the benchmark in section 6 and compare with the 150 ms point in ADR 0023, then measure on the phone. |

Checked and found consistent with the design, by reading: epoch milliseconds throughout the scoring path, so time zone and DST do not matter; scoring uses the injected `Clock.systemUTC()`; future rows are clamped to age 0; pauses are excluded from `listened_ms`; the duration comes from the library `Song`; next, previous (when it moves), auto-advance, repeat one, queue jump, last song and unopenable songs each produce a row; `play_event` has no foreign key and `songsByIds` filters `in_library = 1`, so history survives a retire and return.

Not checked: the scanner's identity matching (ADR 0021), emulator tests, anything in `:app` at runtime.
